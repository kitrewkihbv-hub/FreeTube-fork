# MacTube security and validation notes

Review date: 2026-11-24. This is not a complete security audit or a guarantee of safety.

- `pnpm audit --prod` reported no known vulnerabilities in the production dependency graph.
- `pnpm audit` reported 55 advisories in the development/build dependency graph: 1 critical, 28 high, 22 moderate and 4 low at the time of the check. Examples include tar and undici in build tooling. These are not virus detections, and they were not patched as part of this UI change.
- The account code sends OAuth requests to YouTube endpoints and uses Electron safeStorage for credentials when available; it falls back to unencrypted on-disk storage when encryption is unavailable. Tokens are also made available to the renderer for authenticated API requests.
- The inherited FreeTube window configuration disables Electron `webSecurity`. This is a security tradeoff and was not changed without compatibility testing. Treat untrusted content and a compromised renderer as a risk, particularly with account tokens present.
- The release workflow is configured to download both macOS app ZIPs, extract their app bundles and ASAR contents, update ClamAV signatures, and scan them before publishing. A successful scan checks for known signatures, not every possible threat. Inspect the actual workflow run to know whether it succeeded.
- The rebrand keeps the existing FreeTube data directory in packaged builds; installing side by side therefore shares the same data. Back up your library before upgrading. macOS Keychain behavior and an upgrade from the previous app have not been tested on a Mac; signing in again may be necessary.

Validation includes mocked subscription pagination, fallback and failures (`node tests/youtube-account-subscriptions.cjs`), project lint, and production webpack packs. These tests do not establish live authenticated subscription completeness, macOS installer behavior, or playback against YouTube.

### Discover and Live update

Discover requests YouTube's home browse (`FEwhat_to_watch`) and advances through continuations on refresh, mixing and deduplicating available videos. It prefers a signed-in TV feed when available, otherwise public TV and web feeds. Results can repeat and YouTube may limit or change its responses. Live uses YouTube's `FEtopics_live` browse and only displays items marked live, falling back to a live-filtered search. A private/restricted-mode session uses public requests rather than signed-in recommendations. Subscriptions remain a separate feed; neither discovery feed mutates subscriptions. The palette links to the existing color theme settings, with a separate light/dark button. Both pages can be selected as a startup tab.

Mocked feed/continuation/fallback tests, existing account and player regressions, lint, and production packaging were run locally. YouTube-wide Live, authenticated recommendations, and the Mac application have not been manually tested against a live account or on macOS; YouTube availability and formats can change. ClamAV and a production dependency audit are useful checks but do not establish that an installer is safe. Builds are ad-hoc signed and not notarized.

### Discover refresh follow-up

The dedicated Live discovery page was removed; existing live playback, chat and the subscribed-channel Live view remain. Discover combines YouTube home results with three rotating, randomly selected public topic searches per refresh. This sends those topic queries to YouTube and is not purely personalized recommendations. Results are deduplicated, recent videos are deprioritized, and each source has a 12-second wait limit. YouTube can still return repeated or limited results, and underlying requests may continue briefly after the wait times out. The previous Live startup route redirects to Discover. Mocked tests cover changing topics, fixed home feeds, timeouts, fallbacks, and retained live entry points; no live YouTube account or macOS test has been performed.

### Personalized discovery and subscription follow-up

Discover no longer searches unrelated preset topics. It tries signed-in YouTube TV and WEB home feeds; when signed in, it does not silently fall back to an anonymous home feed. It supplements those results with searches using up to two recent watched titles, weighted towards frequently watched channels. Those titles are sent to YouTube as search queries, and the UI discloses this. If family-friendly mode is enabled, the public restricted feed is used. No claim is made that this reproduces YouTube's ranking or that results will always be new.

The account subscription reader now retrieves up to five pages, tries other account feed formats when the result is small, and supplements small feeds with uploads from up to 40 channels returned as subscribed. Partial results are labeled; subscription changes invalidate cached account feeds and stale requests. Existing local and account feeds remain separate. Automated mocked tests and local packaging passed; account personalization, subscription completeness, playback and the installer have not been tested on macOS or with a live YouTube account.

### Discover refresh paging follow-up

Refresh now reads ahead through small home-feed pages and advances continuation pages for history-related searches instead of reopening only their first page. It prioritizes suggestions not shown recently and clearly labels when only earlier results are available. A repeat-only feed is reordered so it does not appear frozen, but reordering is not represented as new content. Automated tests include clicking the actual Discover refresh button, multi-page recommendations, fixed feeds and expired search continuations. These tests are mocked: the Mac build has not been tested with a live YouTube account, and actual results still depend on what YouTube supplies.

### Related-video refresh follow-up

In addition to home and history-based searches, Discover requests YouTube watch-next recommendations for up to two watched video IDs; when watch history is unavailable, it uses previously returned home recommendations as seeds. These video IDs are sent to YouTube through a public client (with restricted mode when selected). The feed remembers up to 1,000 displayed IDs within the current view session and reports how many suggestions were not previously shown, or when only old results are available. These related requests go to YouTube, not a separate recommendation service; the complete local history is not uploaded by this feature. Tests cover seed rotation, no-history fallback, actual click behavior, source failure, repeated results and parsing two SmartTube TV next-response fixtures (60 and 104 extracted video IDs); they do not establish that current live YouTube endpoints or a signed-in account will work on macOS.

### Subscription refresh follow-up

The signed-in subscription refresh still requests YouTube's subscription feed. If the returned feed adds no video IDs, the view moves a different portion of that same returned feed to the top and offers a button to restore YouTube's original order. This is not a claim that new uploads exist, and the cached feed remains unchanged. A single-item feed cannot be rotated. Mocked view tests cover unchanged, new, failed and single-item refreshes. Live account and macOS testing remain outstanding.

### Authenticated playback and history experiment

Signed-in playback tries the existing TV OAuth session for the player request; youtubei.js attaches its bearer header. It generates the existing video-bound Web proof token via bgutils-js and offers it to the TV request, but compatibility and acceptance are not established. When the TV response is unplayable the existing signed-out path remains; a media 403 before playback retries that path once. Watch-next metadata still uses the existing Web path. Credentials never go to the isolated BotGuard window. OAuth refresh updates are persisted via the existing secure-storage mechanism (with its previously documented plaintext fallback), including an optional rotated refresh token; old sessions cannot save after sign-out.

Account playback can associate viewing with YouTube. When Remember Watch History is enabled and an authenticated TV response supplies both YouTube stats URLs, a best-effort reporter sends playback/progress events to YouTube while the player runs, no more than once per 45 seconds. It only accepts expected HTTPS YouTube stats paths and refuses redirects. Turning that setting off suppresses reporting, but authenticated player requests themselves still identify the account. Existing local history is not bulk-uploaded; it remains separately saved, and YouTube history import remains read-only. YouTube may ignore the reports or apply its own history settings. The account subscription feed reuses requests during a 15-second manual cooldown, and channel-upload fallback runs two requests at once.

Offline mocked tests cover OAuth headers/context, token refresh and optional rotation, sign-out, tracking URL validation/rate limits, local-history handling, fallback and a live-video response. The production pack and production audit are local checks, not real playback validation. No actual YouTube account, home-IP restriction, Apple installer, credential expiry on macOS, YouTube history or live-stream playback was tested.

### Proof-token visitor alignment follow-up

The authenticated TV player now uses a per-video session whose visitorData matches the Web challenge context passed to the existing bgutils-js proof-token generator. The video-bound token is set on that session and in the TV player request body. Per-video sessions share the existing OAuth manager for refresh and do not mutate the shared account session; account credentials are not passed to the BotGuard window. If visitor data or a token is unavailable, the TV attempt is skipped and the previously existing fallback remains. A matching visitor ID does not establish that a Web-issued token is valid for TV or that YouTube will accept the request. The build's youtubei.js 18.3.0 and bgutils-js 4.0.3 were both the npm latest releases checked at this change. Offline tests exercise the actual youtubei.js HTTP serialization, bearer auth, simultaneous distinct visitor/token pairs, missing visitor, fallback and refresh through a per-video session. No live YouTube, personal account, local ISP, Mac installer or playback test has been performed.

### Music view and local widget API

The Electron main process listens on 127.0.0.1:8765 and accepts the unauthenticated GET control API described in README. Loopback binding prevents direct LAN access, not requests from local processes or potentially from hostile web pages: wildcard CORS is intentional at the user's request. No account credentials are included, but the title/channel and playback controls are exposed. The server rejects non-loopback Host names, reports a bind failure without exiting, and stops with the app. Status is supplied by the active Watch renderer and cleared on navigation/closure; no durable history is added. Commands are dispatched asynchronously to the same controls as the music deck; an OK response does not establish that a track or action was available. Artist is the video's channel name. Previous and shuffle require a loaded playlist; next can follow a recommendation. Captions come from the selected video, may be unavailable and are not guaranteed lyrics. Offline HTTP and mocked player-wiring tests do not establish real macOS playback, widget-browser local-network permissions, or YouTube availability.

### Music-only follow-up

The widget listener is started only when at least one renderer is in the Music section (including Music's playlists, legacy music-search route and music-mode watch page) and is closed when the last such window leaves. Ordinary video playback is not reported to or controlled by this API. The interface still uses wildcard CORS and no authentication while active. Search requests YouTube Music's song or music-video search, respecting the app's safety-mode session setting; YouTube controls result availability and may still return restricted content. Search and playback have not been validated against a live account or on macOS. The music palette is scoped to Music routes and does not modify the user's saved theme.

### Übersicht title-file integration

On macOS, the main-window title is written to `/tmp/mactube_np.txt` in the requested pipe-separated format and cleaned up on window close or quit. A private, exclusive temporary file and atomic rename avoid following a pre-existing symlink at the public path; cleanup verifies the last published file identity. Updates are ordered and I/O errors do not crash the app. This reports the main window title even outside Music, including page/search titles, and `PLAYING` reflects a nonempty non-app title rather than actual player state. It is separate from the Music-only HTTP API. Tests cover the file protocol, ordering, permissions, symlink handling, cleanup, and failure; actual macOS/Übersicht integration has not been tested.

### Fresh challenge retry experiment

When an authenticated TV player response is `LOGIN_REQUIRED` or `UNPLAYABLE`, MacTube generates one new visitor ID using youtubei.js's local visitor-data encoding and requests a new BotGuard challenge with that ID in both the Web context and visitor header. It mints a fresh **video-bound** Web token and retries the TV player once with the new visitor, token and existing OAuth manager. A local ID is not a server-issued visitor, and the token is not claimed to be visitor-bound: compatibility of this Web challenge/token with TV or its old page attestation data is unknown. If the retry cannot be minted, is rejected, or the account changes, the original anonymous playback path and proof token remain in use. Initial token failures are reported rather than silently returning an empty token. Offline tests exercise the challenge request, retry, fallback, and session isolation; they do not run real BotGuard or demonstrate YouTube playback. No account credentials are passed to the BotGuard window.

### OAuth expiry and 401 handling

The QR flow stores the TV client identity, refresh token, access token and absolute expiry in the account file. A prior bug left `expires_in` in the persisted credentials; youtubei.js treated that duration as starting over at each sign-in, potentially masking an already-expired token. Old entries are normalized on load and new ones no longer save the relative lifetime. The main process coalesces refreshes across windows using the same YouTube TV OAuth token endpoint as the QR flow, five minutes before expiry and once after a 401. It persists rotated refresh tokens and updates TV/Web/per-video sessions. Authenticated requests retry a 401 once; a second 401 or failed refresh briefly blocks repeated requests, and account subscription, history and playlist fallbacks stop rather than cascading. A persistent 401 may have other causes and may require signing in again. Offline mock and real-youtubei.js serialization tests cannot establish live Google acceptance or real macOS behavior. Local history and the anonymous playback fallback remain separate.

The macOS title file now has four fields (`IDLE|MACTUBE|STANDBY|` or `PLAYING|title|MACTUBE|thumbnail`), updated on title and in-page navigation. Video IDs are validated and the thumbnail points to `i.ytimg.com/vi/<id>/mqdefault.jpg`; requesting it discloses the video to YouTube. As before, `PLAYING` means a nonempty window title, not actual playback, and the feature has not been tested in Übersicht on a Mac.

### Embedded streams with separate TV watch reporting (supersedes the earlier TV-player experiments)

Stream extraction now uses an anonymous per-video WEB_EMBEDDED player session rather than an authenticated TV `/player` request. Its visitor data comes from the Web BotGuard challenge; its video-bound proof token is attached to the session and player request. A rejected `LOGIN_REQUIRED` or `UNPLAYABLE` response can trigger one fresh locally generated visitor and challenge, after which the existing anonymous Web path is retained as a fallback. Web proof-token acceptance by the embedded client is not established. A selected embedded stream that fails with an early media 403 retries the Web path. Watch-next metadata continues to use the Web response.

When signed in and Remember Watch History is enabled, the reporter attempts TV OAuth playback and watchtime pings using tracking URLs from the selected player, or from the original Web response only if it explicitly identifies the same video. It never invents missing tracking parameters; if the URLs are missing or invalid, reporting is unavailable. YouTube may reject or ignore tracking URLs generated by another client. Local history remains independent. Existing URL allowlists, redirect rejection, sign-out checks and throttling remain. Age/trailer fallback reporting is skipped when the tracking source is ambiguous. Offline tests check actual youtubei.js serialization, absence of bearer credentials on embedded playback, TV bearer on stats, selection, retries, fallback and sign-out; they do not prove actual YouTube playback, cross-client history reporting, or macOS behavior.

### Embedded identity and Android VR fallback

Electron's existing network interceptor already set YouTube Referer and Origin for InnerTube requests, but youtubei.js's `WEB_EMBEDDED` client override silently replaced the supplied `thirdParty.embedUrl` with its own Google URL. The embedded session now serializes `https://www.youtube.com/` without that override, including the separate embedded age/trailer fallback; Electron normalizes the restricted headers case-insensitively. If the embedded response is rejected (including `ERROR` / embedder identity denied), lacks playable streams, or throws, MacTube tries one anonymous `ANDROID_VR` player request and then the existing anonymous Web path. The VR session carries the current Web challenge visitor and proof token; compatibility with Android VR is not guaranteed. Electron sets youtubei.js's pinned Android VR User-Agent only for VR `/player` requests, not account requests. Early media 403s advance from embedded to VR to Web without looping. TV OAuth remains reserved for account functions and best-effort watch reporting; local history is unchanged. Offline tests check the actual serialized embed context and VR body, request header transformations, error-152 selection, fallbacks, tracking and sign-out. They do not prove YouTube accepts the embedder identity, VR token or cross-client watch pings, or that any content plays on a real Mac. Creator and account restrictions still apply.

### Authenticated TV-embedded playback experiment

The user reported a signed-out Android VR bot challenge and embedded error 152. Those responses establish rejection but do not prove a CGNAT/IP cause. MacTube now first attempts a per-video `TVHTML5_SIMPLY_EMBEDDED_PLAYER` session with the TV account OAuth manager, the Web challenge visitor, a video-bound Web proof token, and an experimental Tizen-style user agent. The context contains the YouTube embed URL, and Electron sets the matching YouTube Referer/Origin and user agent only on the scoped request. If rejected or unavailable, playback falls back through anonymous embedded, Android VR, then the original Web path; an early media 403 advances to the next client. A `LOGIN_REQUIRED` or `UNPLAYABLE` authenticated response can request one fresh visitor/challenge and retry once. Accounts, subscriptions and local history are not mutated by the per-video session. The main TV account session is unchanged and still handles OAuth refresh and optional authenticated history pings. **Authenticated player requests disclose the watched video ID to YouTube even when Remember Watch History is disabled**, and YouTube may associate them with the account independently of MacTube's history setting. YouTube may reject the Web-minted proof token, OAuth/client pairing, device identity or embedding; neither playback nor remote history is guaranteed. Tests exercise real youtubei.js request serialization, OAuth header refresh, visitor/token pairing and concurrent session isolation, fallback stages, logout races and history wiring offline. No live YouTube account, T-Mobile network or Mac playback test was performed. Origin and Referer are intentionally not added to unrelated websites.

On macOS, `/tmp/mactube_cmd.txt` is a single-slot local widget command mailbox, polled about every 300 ms. `PLAY` toggles playback, `NEXT` uses MacTube's playlist or recommended next video, and `PREV` restarts after four seconds, otherwise goes to the previous playlist video or browser history. Commands target the window represented by the title file, and require a loaded watch player. A private claim directory, regular-file/owner/size checks and no-follow open avoid reading a symlink as a command; writes can still overwrite each other before polling. Any program running as the same macOS user can control playback via this file. No authentication is provided. The widget file is not in this repository and real Mac/widget behavior remains untested.

### Local Spotify-style player adapter (experimental)

The existing Music-only `127.0.0.1:8765` server additionally implements `GET /v1/me/player`, `GET /v1/me/player/currently-playing`, `PUT /v1/me/player/play`, `PUT /v1/me/player/pause`, `POST /v1/me/player/next`, `POST /v1/me/player/previous` and `PUT /v1/me/player/seek?position_ms=...`. Idle status is 204; commands require a loaded Music player and acknowledge dispatch, not guaranteed playback. A seek requires a known duration. Next/previous follow existing MacTube behavior and may do nothing if no next/previous is available. `/status` and the old commands are unchanged. Playback progress is reported approximately once per second. Metadata uses YouTube IDs, `youtube:video:` URIs, YouTube external links and YouTube thumbnails, not Spotify track IDs; album is labeled YouTube, and repeat state is unavailable. Requesting a thumbnail contacts YouTube.

This is not Spotify's service or OAuth and it does not implement account, catalog, queue, device transfer, volume, repeat, shuffle control or starting arbitrary Spotify tracks. It requires a widget that can be pointed at the local API and does not magically intercept requests to api.spotify.com or AppleScript. Do not send real Spotify credentials or bearer tokens to this API. Spotify-style routes reject browser-origin requests and do not offer CORS; host checks mitigate DNS rebinding, but any local process can query/control the Music player without authentication and impersonate the server if it occupies the port first. The pre-existing legacy API still has unauthenticated wildcard CORS. This server stops outside Music mode. The adapter was tested locally with mocked playback, not with a real Spotify widget or macOS installation.
